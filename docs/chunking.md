# EPUB 语义分块与安全回写方案

日期：2026-10-06\
状态：方案定稿，待实现；本文不表示现有代码已经满足全部要求。\
约束来源：本次讨论中用户的最新要求。若与较早方案冲突，以本文列出的硬性约束为准。

## 1. 范围与不可变原则

目标是在保留原有翻译 workflow 的基础上，改进翻译前的解析、术语准备、chunk 规划和翻译后的格式回填。

完整顺序：

```text
读取 EPUB、识别资源类型
→ 安全解析并建立原文/结构映射
→ 识别不可拆分单元和完整保留对象
→ 提取、合并并冻结术语
→ 按完整请求预算合并相邻单元
→ 原 workflow：translate → proofread → apply_corrections
→ 保存译文 JSON
→ 按原位置统一回填
→ 校验并生成 <原文件名>-cn.epub
```

不得借本任务重写另一套翻译执行器。原 workflow 的步骤顺序、调度能力和保存流程应保留；需要适配的是输入表示、按 ID 应用修订、结构校验和回填接口。

硬性原则：

1. p、table、em、i、ul、ol 不得跨翻译项或跨请求拆分。
2. 相邻完整单元尽量合并，但不能突破配置和模型预算。
3. 原文不得遗漏、重复或因为节点过大而静默跳过。
4. 每次请求最多附带最近 1–2 个源片段作为上下文，整批共享一次。
5. 模型只返回翻译/校对所需结果，不生成完整 EPUB 文档结构。
6. 结构、属性、资源和回填位置由本地映射控制。
7. review 返回有效修订后必须实际应用并保存，不能反复校对同一份旧译文。
8. 不以截断控制输出长度，不将截断结果写入最终书籍。

**明确撤销较早方案中的以下做法：长 p 按句子拆、table 按行拆、ul/ol 按 li 拆，以及在 em/i 内生成跨请求续接片段。**

## 2. 术语与数据边界

| 名称 | 含义 |
|---|---|
| 原始资源 | EPUB 中原始 XHTML/XML/HTML、CSS、JS、图片等文件 |
| 结构映射 | 原始节点、属性、文本位置和占位符的本地对应关系 |
| 原子翻译单元 | 必须一次完整翻译的内容，例如一个 p、一张 table、一个 ul |
| chunk | 一次模型请求中按阅读顺序组合的一个或多个原子翻译单元 |
| 完整保留对象 | 不翻译、只以占位符表示的原始子树或资源 |
| 上下文 | 供理解使用的只读前文，不属于当前待译内容，不重复回填 |

一个 chunk 可以包含多个完整 p/table/ul，但一个 p/table/ul 不能分散到多个 chunk。表格和列表也不能拆成多个相互独立的翻译项后声称已经满足“整体翻译”。

## 3. .env 配置和 token 口径

新增配置：

```dotenv
# 每个请求中待译内容的 token 上限
EPUB_CHUNK_MAX_TOKENS=2000
```

需要更大批次时：

```dotenv
EPUB_CHUNK_MAX_TOKENS=5000
```

配置规则：

- 必须是正整数，非法值在启动时明确报错。
- 原有显式 --limit 参数优先于 .env；未显式指定时读取 .env，默认 2000。
- 不再增加一个隐藏的固定 1200-token 拆分上限，覆盖用户设置。
- 此上限计算本批序列化后的 item_id 与 source 内容，包含必要占位符和这部分 JSON 开销。
- 提示词、术语、上下文和其他必要结构说明不计入上述待译内容上限，但必须计入完整请求输入预算。
- review 的完整输入还包括已有译文。

同时满足以下约束，才允许派发：

```text
S：本批待译内容 token 数
I：完整模型输入 token 预算
R：完整结果所需的输出预留
M：模型上下文安全余量

S <= EPUB_CHUNK_MAX_TOKENS
I + R + M <= 模型上下文上限
R <= 已配置且模型支持的输出上限
```

初译和 review 都需要检查。review 的输出规划不能仅按“全部通过、只返回简短结论”估算，还要考虑返回完整修订内容的情况。

模型上下文上限、输出上限和 EPUB_CHUNK_MAX_TOKENS 是不同参数，不能互相代替。将 chunk 上限设成 5000，并不代表 4096-token 的输出额度一定能容纳完整译文。

使用与模型匹配的 tokenizer。无法精确匹配时，使用明确标注的估算和经过实测校准的安全余量；不得将字节数显示为实际 token 数。保存 tokenizer 名称、版本和估算策略，并区分本地估算与接口实际 usage。

参考：[tiktoken 官方说明](https://github.com/openai/tiktoken)。

## 4. 不可拆分标签及嵌套规则

| 标签 | 处理规则 |
|---|---|
| p | 完整段落作为一个翻译项，包括所有可译文字和内联结构 |
| table | 完整表格作为一个翻译项，不拆表头、行、单元格或跨行结构 |
| ul、ol | 完整列表作为一个翻译项，包括嵌套列表 |
| em、i | 完整范围保留在同一个翻译项中，不能在其内部切分 |
| 普通 div、section、article | 可沿内部完整单元的边界下钻与分组 |

使用“最外层不可拆元素拥有其整个翻译范围”的规则：

- p 中的 em/i 随 p 一起处理，不另建翻译项。
- table 中的 p、ul/ol 随 table 一起处理。
- ul/ol 中的 li、p 和嵌套列表随外层列表一起处理。
- 独立出现、没有上述原子祖先的 em/i，本身就是不可拆单元。
- 父单元已拥有的内容，不能再作为子单元重复发送。

标题优先与后面的首个完整内容单元合并；若预算不允许二者同批，允许在两个完整元素之间断开，但不切开标题后的 p 来强行凑数。

普通容器的直接文字必须保留。例如：

```html
<div>
  前面的说明
  <p>中间段落</p>
  后面的补充
</div>
```

前面的说明、中间段落、后面的补充都必须登记。遍历需要覆盖 element.text、子元素及 child.tail，不能只处理带标签的子节点。

普通 div 的直接文字与内联内容可以组成虚拟文本块。虚拟块超限时，只允许在不穿过任何不可拆子树的安全文本边界处分组；这不构成在 p/em/i 内拆分的例外。无法安全分组时同样进入超限处理。

## 5. 多层容器如何合批

示例：

```text
外层 div
└── 中层 div
    └── 内层 div
        ├── 原子单元 A
        ├── 原子单元 B
        └── 原子单元 C
```

1. 沿 DOM 阅读顺序提取 A、B、C，祖先容器和属性留在本地。
2. 先尝试 A+B+C，检查待译内容、完整输入和完整输出预算。
3. 如果超限，而 A+B 能放下，则形成请求 A+B 和请求 C。
4. 如果 A+B 也超限，则在 A 与 B 之间结束当前批次。
5. 如果 B 本身是普通布局容器，可以继续寻找其内部完整单元。
6. 如果 B 本身是 p/table/em/i/ul/ol，不得继续往内部拆分。

三个祖先 div 不会为每个 chunk 重复生成。最终回填的是原始结构中的 A、B、C 位置，不是拼接多份带祖先外壳的 HTML 字符串。

合批采用顺序贪心方式：每增加一个完整单元就重新测量请求；超过任一预算则结束当前批次。禁止先越界发送再依赖模型截断。

不同正文文档、导航、元数据和注释等不同内容类型保持明确边界。短小节可以合并，不应因为出现一个普通包装 div 或标题就无条件创建一次 HTTP 请求。

## 6. 不可拆单元超限时的唯一处理

不可拆约束与 token 硬上限有可能无法同时满足。例如完整 table 为 2600 tokens，而上限为 2000。

必须在正式付费翻译前预检并列出：

- 原子单元 ID、源资源路径和源位置。
- 标签类型及待译 token 数。
- 当前 chunk 上限。
- 完整输入预算和预计完整输出需求。
- 超限原因：待译内容上限、完整输入限制或输出额度不足。

禁止静默拆分、截断、删内容、自动放宽上限或发送超限请求。必须先调整配置使该完整单元能够容纳，或另行明确改变约束；本方案不包含自动例外。

若只是附带信息使完整输入超限，可以减少可选前文或去掉无关术语；若原子单元本身超过待译内容上限，减少上下文并不能解决该问题。

只包含完整保留对象和空白的单元不需要模型翻译，也不应因为原始代码或 SVG 很大而误判为巨大的待译正文。

## 7. XML/XHTML 与 HTML 的解析选择

先根据 EPUB manifest 的媒体类型、命名空间和文件内容确定类型，扩展名仅作为辅助信息。不能看到根标签是 html 就使用 HTML 解析器。

| 资源 | 方案 |
|---|---|
| XHTML 正文 | lxml.etree 的严格 XMLParser |
| NCX、OPF 等 XML | lxml.etree 的严格 XMLParser，并使用字段白名单 |
| 真正 HTML | HTML5 解析用于识别和诊断；必要的规范化单独进行并验收 |
| 未识别用途的 XML | 不自动遍历并翻译所有文本节点 |

XML/XHTML 要求：

- 保留命名空间和 XML 标签大小写。
- 保留空白、注释、处理指令和 CDATA 信息，不自动美化缩进。
- 不启用 recover 模式静默修复错误 XML。
- 禁止外部网络和任意本地文件实体访问。
- 标准 XHTML 实体使用受控离线解析；未知实体或不安全声明明确报告。
- 节点识别使用命名空间 URI 与本地名称，不能依赖一个固定前缀。

XML 资源的翻译白名单：

- NCX：导航标签和文档标题等可读文本。
- OPF：书名、简介等明确指定的元数据。
- manifest、spine、资源路径、标识符、媒体类型和链接关系保持不变。
- 作者名、参考文献专有名词按保留规则处理，不因包含英文就判失败。

html5lib 不能作为“无损回写核心”。其 HTML5 修复可能调整树结构，序列化也可能省略可选标签或处理编码声明。真正 HTML 的规范化如果改变了不可拆元素的边界、CSS/JS 内容或造成映射歧义，必须报告，不能直接进入翻译。

不默认增加 html5lib 作为 EPUB 主路径依赖；确实需要支持真正 HTML 的规范化时，再引入并单独验证。

## 8. 占位符与完整保留对象

采用两类控制标记：

| 类型 | 示例 | 含义 |
|---|---|---|
| 可译内联范围 | ⟦+g1⟧文字⟦-g1⟧ | 原节点和属性保存在本地，内部文字可翻译 |
| 完整保留对象 | ⟦=x1⟧ | 整个原始子树或不可译片段保留，模型不能重写 |

示例原文：

```html
<p id="p1">Use <em>this command</em>: <code>pip install demo</code>.</p>
```

模型输入：

```json
{
  "item_id": "p1",
  "source": "Use ⟦+g1⟧this command⟦-g1⟧: ⟦=x1⟧."
}
```

模型返回：

```json
{
  "item_id": "p1",
  "target": "使用⟦+g1⟧这个命令⟦-g1⟧：⟦=x1⟧。"
}
```

该 p 仍是一次完整翻译，g1 和 x1 不是新的独立任务。

默认整体保护：script、style、pre、code、kbd、samp、svg、math，以及不需要翻译的音视频/嵌入资源子树。

处理规则：

- 保存完整原节点、属性、内容和来源映射。
- 不把大量代码、CSS、JS、SVG 路径、公式源码或 Base64 数据送给模型。
- 完整保护父节点后，不再为其后代生成任务。
- 受保护节点的 tail 属于外部文本，不能连同节点一起丢弃或重复恢复。
- img 的资源引用和结构保留；允许翻译的 alt/title/aria-label 等属性单独登记，恢复节点后按白名单回填。
- 完全禁止翻译的区域不修改其属性。translate=no 的继承及后代显式重新启用翻译，需要在提取阶段识别；有可译岛时不能粗暴保护整棵父子树，且仍须遵守外层原子单元边界。

占位符按 item_id 隔离。必须检查清单、出现次数、配对、嵌套和移动边界；禁止跨项引用、丢失、重复或增加未知标记。

原书自带类似控制标记的字面文本，必须先转为保留对象，防止与生成标记冲突。实际回填使用映射与结构化事件，不做全局字符串 replace。

## 9. head、CSS/JS 与回写保证

不能宣称 lxml 或 html5lib 对任意输入都支持逐字节无损回写。必须区分：

1. 能正确解析。
2. 回写后结构和文本语义一致。
3. 未修改区域的原始字节完全一致。

第三项不是普通 DOM 序列化器自动提供的能力。

本方案的目标约束：

- head 默认作为受保护源模板区域，不交给模型，也不因正文翻译而重新生成。
- title 或指定描述字段若需要翻译，作为单独白名单文本位置处理。
- 内联 style/script 的原始内容必须保留；外部 CSS/JS 文件直接复制并核对哈希。
- 翻译阶段不负责重写或优化 CSS/JS。
- 正文回填只触及登记的源位置。不能把整份文档交给序列化器后假定 head 完全没变。
- 要达到非翻译 head 区域逐字节保留，应保存原始字节及其区间，原样复制未修改区域。
- 不使用简单的 head 起止标签正则定位，因为注释、CDATA、脚本文本中也可能出现类似字符串。

XML 可使用标准库 xml.parsers.expat 的事件字节位置辅助建立源区间映射，lxml 用于语义树和结构校验。这是待实现、待原型验证的适配层，不能假定现有源码已经具备。

源区间映射必须验证编码、BOM、CRLF、CDATA、实体、自闭合标签、命名空间和注释。所有替换区间基于同一份原始文件，并检查无重叠；不能因先前替换改变了长度而继续使用错误偏移。

**不能定位可靠原始区间时，报告回写不受支持，禁止悄悄降级为整份文档重写。**

真正 HTML 与 XML/XHTML 的脚本和样式转义规则不同。不得把 HTML 解析结果直接以 XML 写出后，仍按 HTML 方式交付；反方向也不能混用。需要转换格式时，将转换作为单独的准备步骤并验证，不混进翻译。

## 10. 已核查的库行为与证据

| 项目 | 结论 |
|---|---|
| lxml XMLParser | 适合 XHTML/XML；支持命名空间和 CDATA 保留配置，但不是源码无损编辑器 |
| lxml HTMLParser | 会尝试修复错误 HTML，官方不保证恢复树保留全部原始数据 |
| html5lib | 面向 HTML5 解析与规范化，不承诺保留原始源码写法 |
| Python xmlx | 与 lxml 是不同项目；公开说明不足以证明满足复杂 EPUB 的无损回写需求，不列为本方案依赖 |
| tiktoken | 用于明确口径的 token 计数；第三方模型仍需核对 tokenizer 匹配关系 |

本次对当前环境 lxml 6.1.3 做过最小内存实验，样本含 XHTML 命名空间、head、style、script、CDATA 和 CRLF：

- CSS 文本、JS 文本、head 子节点顺序保持一致。
- 使用 strip_cdata=False 后，样本 CDATA 保留。
- 整份文件字节不完全相同。
- 同一段 HTML 脚本以 HTML/XML 两种方式序列化，字符转义不同。

这些结果仅证明合法样本的相应行为，不证明所有 EPUB 都能完美回写。html5lib 的结论来自官方资料，本次没有声称已进行其本地全量兼容测试。

## 11. 上下文和模型可见信息

- 整个 chunk 最多附带最近 1–2 个源片段，每个参考片段最多 400 字符。
- 400 字符只限制附带前文，不限制待译正文。
- 前文只发送一次，明确标为只读，不重复生成译文或回填。
- 当前批次已经包含的内容不再作为上下文重复发送。
- 不发送整章背景、祖先 DOM 外壳、文件哈希、XPath、源偏移和历史版本清单。
- 必需标记语义及与本批正文匹配的术语保留；用户术语备注不能无声丢弃。
- 不同类型的附加信息全部计入完整输入预算，不能通过改字段名称绕过预算。

完整 table 和完整 ul/ol 的内部结构本来就在当前翻译项中，不需要因拆行或拆 li 额外复制表头、列表引导语。这消除了较早方案中的部分结构依赖冲突。

## 12. JSON、断点与配置变更

工作资料保存在原 EPUB 旁、以原文件名不含扩展名命名的目录内。已存在的任务可以保留内部的 source_hash/run_id 子目录，以维护原断点身份。

本地至少保存：

- 原始 EPUB 及资源哈希。
- 解析器、提取器、拆分器、提示词和结果格式版本。
- 模型、tokenizer、预算策略、chunk 上限和术语表哈希。
- 源节点、文本/属性位置、原子单元归属、原始区间及占位符映射。
- chunk 的有序成员、实际请求、响应、初译、校对结果及错误。

映射 ID 与一次请求的批次 ID 分开。一个批次失败不应破坏其他已保存单元。

初译后立即保存；校对的有效修订应用后立即保存。只重试当前冻结方案中的失败项，不重新翻译已完成内容。

续跑使用已保存的拆分方案和配置。修改 .env 默认影响新任务；不能无提示地改变旧任务的分块及其已付费结果。如需重排未开始的请求，必须单独执行明确的重规划，只处理未发送范围，并保存配置变化与映射关系。

更换模型、术语、提示词或解析规则时，评估受影响的结果，不无条件复用。

## 13. 与原 workflow 的集成边界

保留原来的三个步骤：

```text
translate
→ proofread
→ apply_corrections
```

适配要求：

- translate 输入完整原子项及其必要标记，输出 item_id 与完整译文。
- proofread 对照当前原文和当前译文，返回按 ID 定位的修订结果。
- apply_corrections 真正应用修订并校验，不能只记录 suggested_target 后继续 review 旧稿。
- 禁止用模糊全文替换猜测修订位置。
- 结构不合法的修订不能保存为最终成功，也不能把未解决的问题伪装成完成。
- 日志区分等待响应、收到响应和应用结果；显示本批新增初译、校对通过、已保存修订、重试及待处理数量。

不整体移植当前新执行器的恢复层、人工补译分支或状态机。现有格式保护代码只选择性复用经过验证的能力，并为旧 workflow 做最小接口适配。

| 大段代码、SVG、公式 | 完整保护，不发送其大段源码 |
| 原文含与控制标记相似的字面文本 | 不误识别为生成标记 |
