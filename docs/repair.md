# 翻译失败修复

## 证据与范围

依据用户粘贴日志和 `agentic-ai-platform-engineering-rethinking/state.json` 中的请求、原始响应、片段记录，以及解压后的原文。诊断期间用户仍在运行翻译，因此历史失败与当前待处理状态分别判断；已经成功的记录不重新翻译。测试使用临时副本，不改动正在运行的书籍状态。

## NCX 单独处理

实际 `toc.ncx` 有 199 个标题，约 1549 正文 tokens；184 个能从已接受正文标题派生，剩余 15 个需要模型。先收集整份 NCX 的标题与节点映射，派生和翻译记录共用现有 JSON 断点。把同文档待翻译标题合并为批次，再合并校对，回写只改变对应 `text` 文本。

NCX XML 层级、`navPoint`、`id`、`playOrder`、`content/src` 全部本地保留。正常运行和恢复都复用已经成功的标题。正文 token 少不代表全部 199 项的完整校对响应能装进 4096 tokens；只有实际输入/输出限制要求时才在标题之间拆请求。禁止跨文件混合、重新翻译成功标题，或把整份 NCX XML 交给模型重写。

## 实施和验证顺序

1. 建立网络重试、实际索引截断、缺失/空槽的失败复现。
2. 并行修复网络边界和预算/重试分组；槽位纠错与 NCX 验证保持各自文件所有权。
3. 用真实书籍的原文、请求及原始响应重放验证，核对回填后的 XML、索引锚点、代码与 NCX 链接。
4. 运行相关测试、完整测试、lint 和类型检查。任何验证缺口明确记录。

不新增依赖，不修改正文最大/最小 token 配置，不输出最终长错误列表，不改动用户正在使用的书籍状态。维护文件保持单词命名且不超过 1000 行。

## 后续日志：准备阻断与完成后打包

`generative-engine-optimization-ai-seo` 的五个准备阻断项是完整目录 `ol` 和四个索引 `ul`，有 131–358 个文本槽。完整响应预留为 4162–6774 tokens，默认 4096 无法容纳；目录单项即使不加第二层安全余量也超过 4096。不能拆开这些标签或把原文当译文回填。

默认输出容量调整为 8192（低于 [Agnes 官方说明](https://wiki.agnes-ai.com/en/docs/agnes-30-flash) 中的 65536 输出能力，2026-10-08 已核对），显式指定的容量继续生效。自动升级仅针对输出默认值 4096→8192、预算版本→6 的变化，且其它配置一致。

旧状态只有在未发送任何模型请求、没有术语计划/候选池/冻结词表/用户词表、没有 ready 或正文计划时才本地重建。复用原书快照，保留原术语提取配置，不声称重绑定已经完成的术语工作。已有术语或正文工作的任务保持原来的冻结配置。显式 provider、model、concurrency、glossary 等冲突在清理旧准备记录之前拒绝。

格式密集的索引还存在另一种冲突：真实 Index.xhtml 的 321 项正文共 1680 tokens，但旧 4096 输出容量下没有任何能满足 500 正文 tokens 的安全批次。新预算允许已经证明无法合并的输入/输出/上下文容量例外，记录 `minimum_unavoidable`，不能把整章标成不可翻译。可合并的小块仍必须合并，不改变环境里的正文目标与最小值。

GEO 在输出容量修正后还暴露了输入问题：四个列表的模型请求中，重复结构约束占 8400–10470 tokens。文本槽响应不能修改标签，程序本地也会恢复和校验全部标签，所以这部分模型输入是重复的。v6 保留原来的四种请求拟合方案，仅在全部失败后新增最后一次拟合：省去模型输入中的结构约束，保留源文、标签提示、术语与完整本地 registry，再重新计量。旧 v5 和原本能装下的 v6 请求均不改变，不提高默认 32768 上下文限制，也不重绑定已经处理的词表。

2398/2398 表示初译、校对和回填单元已经完成；生成 EPUB 还需校验与组装。发布路径原来重复构造 ReadySession/BodyJournal、核对同一整本书的请求证明。现复用翻译阶段的会话，在独占锁内只重建一次目标证明，并在发布前后核对状态指纹，保留直接篡改检测。增加组装开始、完成两个阶段提示。206 单元的完整发布回归由约 8 秒降至 1.15 秒；此性能数字来自受控断点，不冒充整本实书的耗时。
