**版本：2.5｜自动术语提取、JSON 保存与冻结词表整合终稿**  
**日期：2026-09-29**  
**输入：英文 EPUB；输出：简体中文 EPUB；运行方式：沿用现有本地程序。**

> 本文是本次重构的唯一实施基准，完整替代 v2.4 及更早版本的实施规定，而不是在旧文档后追加补丁。旧版 68 项讨论作为历史分析保留，不再要求开发前逐条证明全部候选风险。本文没有审计实际源码，也没有宣称项目测试、真实模型或阅读器验收已经通过。

> **MVP 主线：读书 → HTML/XHTML 解析并保存 JSON → 自动提取并保存术语候选 → 用户词表优先合并与本轮词表冻结 → 从 JSON 翻译/校对 → 局部失败继续、逐项保存 → 本地重建和完整验证 → 中文 EPUB。**

## 0. 产品目标、保证边界与不做的事

### 0.1 MVP 完成目标

在支持范围内，用户提交一本英文 EPUB 和现有模型配置后，程序应能完成正文及必要辅助文案的简体中文翻译，保留文档结构、代码、图片和引用，支持中断续跑，并生成中文 EPUB 和可定位问题的报告。

**只保留一种正式完成标准。** 所有应译单元通过本地检查和指定版本的机器校对，相关衔接检查完成，结构与 EPUB 检查通过，才返回 `completed`。MVP 不新增快速模式、跳过校对模式、部分英文混排草稿导出或多档质量配置。失败或未完成结果保存在工作目录；**本轮调度必须继续处理后续所有可执行的独立任务**，不能等失败项修好才翻下一段或下一章。只有最终发布受整书完成门槛限制，不是每个翻译任务都受该门槛限制。

“格式完整”允许中文段内改序，但不允许章节、段落、列表、表格行列被模型重组；不允许链接、图片或代码丢失。“机器校对通过”不等于零错译，更不等于人工精校。最终规范检查也不证明语义和所有阅读器显示效果。[^R4]

### 0.2 必须保留的能力

- 完整语义单元翻译、必要源上下文、自动术语提取/候选存档、用户词表优先合并、冻结快照、源译校对与有限修订。
- 段内允许的格式对象改序、合法嵌套、代码/公式/图片保护、白名单属性翻译。
- 超长单元切分与重组、整书内容归属检查、导航与语言更新。
- 有界并发、失败隔离后继续、有界重试、章节解析 JSON 和单元结果 JSON、断点恢复、失败定位及可靠输出。

### 0.3 不纳入 MVP 的建设任务

不建设编码探测或转码体系，保持现有 UTF-8 约定；不做 OCR、图片重绘、DRM 解密、固定版式重排、原音频重新配音或同步、动态脚本翻译、任意格式范围拆合。

不建设 Web 后台、数据库迁移、分布式队列、通用翻译平台、向量库、全书逐词对齐、滚动摘要传播、运行中动态词表/实体属性共识平台、智能多模型路由、CSS 级联/布局引擎、自动样式物化或字体剪枝系统。

**不因为减少功能而删除正确性检查。** 限定输入支持范围、简化状态与修订策略，而不是关闭校对或让异常内容静默保留英文。

### 0.4 关于现有 epubox

原模块路径来自用户提供的清单。实施时读取真实入口、配置、依赖、相关函数和已有测试，保留已有效的能力；不预设 Python/SDK 版本，不无故更换框架，也不将“存在风险描述”等同于“源码已确认有 bug”。无需先完成一份 68 项全面审计才能开始 MVP 闭环。

本版在完整阅读 v2.4 后，按用户确认的“模型发现术语、Python 校验与保存、翻译前冻结”逻辑更新。上游流程与函数依据沿用前两轮对 `deusyu/translate-book` 的源码研究；此次是设计整合，不重新声称审计了最新 HEAD。历史上未锁定可核验提交，实际复制代码前仍须固定提交并核对许可。[^U0][^U1][^U5][^U7]

## 1. 明确支持范围与提取范围

### 1.1 输入支持边界

正常目标是当前项目可解析的 EPUB 2/3、可重排、静态英文书。代码、数学公式、图表、复杂列表和脚注是正常内容，不能仅因包含这些内容就排除整本技术书。保留源 EPUB 版本，不顺带升级格式。

付费模型调用前检查：源包可读取、路径安全、所需资源可找到、XML 可按项目适配器解析、模型/检查工具可用、输出路径可写，以及支持范围是否满足。

下列情况给出准确原因并停止正式翻译，不实现额外修复系统：正文加密、需脚本生成的阅读内容、固定版式或多版本混合阅读包尚无适配、被译正文绑定未支持的音频同步、源文件含不能处理的签名关系。**字体混淆不等同于正文 DRM**：已支持的字体混淆资源和标识符按原样保留，不做解密/重命名。普通图片、独立音视频不因此被拒绝；仅保留其资源，不宣称其中英语已翻译。EPUB 的阅读顺序、字体混淆、签名与媒体同步各有独立约束。[^R1]

XML 解析沿用已支持当前 EPUB 的适配器，禁止随正文内容联网取外部实体或读取任意本机文件；已有 EPUB 2 所需的可信本地解析支持不因重构被误删。本地引用与外部链接分开处理，不把外链原样保留解释成已验证其在线可达性。

MVP 不自动修复源书。源规范检查中的 ERROR/FATAL 在调用模型前报出并阻断；WARNING 记录但不自动升级为失败。没有安装规范检查工具时在预检失败，不先花翻译费用再生成不合格的“候选完成品”。

### 1.2 内容处理决策

| 内容 | MVP 决策 |
|---|---|
| 正文、标题、引文、列表、表格自然语言、图注、脚注/尾注、旁注 | 翻译；保留源结构归属 |
| XHTML 导航、NCX 标签、章节 `head/title` | 纳入同一任务账本，按 §11 处理复用 |
| 已存在的 `alt`、`title`、`aria-label`、`aria-description` 自然语言 | 白名单属性单元；空值保持空，不补写图像描述 |
| `id/href/src/class/style`、ID 引用型 ARIA 属性、状态值、命名空间及资源路径 | 本地保留，不交给模型改写 |
| 代码块、命令、代码输出、短内联代码 | 原内容保留；短且必要的代码作为只读提示可见 |
| 图片、公式、SVG/MathML 绘图内部及其嵌套说明 | MVP 作为整体资源/子树保留；图外说明照常翻译，不声称图内英语已处理 |
| 已有中文或明确不译内容 | 保留；含英语的混合段仍按完整语境处理其应译部分 |
| OPF 主书名、文字型简介 | 默认翻译；多语言备用标题原样保留；归属不明确则保留该元数据并报告 |
| 作者、ISBN、出版商、原出版日期、标识符 | 不改写；必要目标语言/修改时间另按 §11 处理 |
| `script/style` 源码、注释、纯结构空白 | 不作为自然语言任务，保留并记录类别 |

主输入是英文书，不新增通用多语种识别和繁简转换功能。新生成目标要求简体；已有中文按源保留。不能以“段落含汉字”直接跳过其中的英文。

### 1.3 范围判断优先规则

硬保护的代码/公式内部不是翻译区域。其余区域按明确内容规则、HTML 的有效 `translate` 状态和白名单处理；继承 `translate=no` 时，不翻译该处文字与可译属性，后代显式 `translate=yes` 的处理按适配器规则恢复，但不能越过代码/公式硬保护。用户例外规则在准备阶段显式编译，不能在某次重试中临时改变。[^R5]

正文 `translate=no`、图内文字保留、代码保留是事先声明的合法范围，不是“模型失败后跳过”。需要翻译却失败的单元不能自动改成保留类。

manifest 与 spine 分开使用：盘点所有相关 XHTML 资源，spine 仅决定主阅读顺序；尾注、`linear=no`、导航等独立资源照常纳入。相同资源只提取一次。未声明但被引用的阅读资源进入预检，不在完成率分母中悄悄消失。

## 2. 单机流水线与数据归属

```text
源 EPUB + 运行输入配置（含用户词表和提取配置）
  → Prepare：源快照、资源盘点、全局预检
  → Parse & persist：各 HTML/XHTML 原文、源槽位、Unit、格式引用写入 document JSON
  → Parsed ready：提交 preparation.json；只允许术语准备调用
  → Extract terms：从 JSON 视图逐窗提取，候选/失败逐项保存，后续窗口继续
  → Consolidate & freeze：校验证据、用户优先合并、有限核对，冻结 glossary.json
  → Translation ready：词条绑定、CutPlan/初始 UnitRecord，最后提交 bookplan.json
  → Plan from JSON：只读恢复规划 action/reasons，不写状态
  → Translate & review：固定词表和源语境；局部失败继续其他任务
  → Coherence：依赖齐备的章节检查，其他章节不被失败章阻塞
  → Assemble & finalize：源模板+已接受译文，导航/语言/有限排版
  → Validate & publish：临时包重开、结构/资源/规范检查后提交真实产物
```

**两个准备门槛不能混用：** parsed_ready 允许术语提取和候选核对的付费请求；bookplan ready 才允许正文/属性/导航/元数据的正式翻译及校对。bookplan 尚不存在不代表没有发生过模型调用；准备期的费用和提取成果也必须可恢复。

### 2.1 数据对象

| 对象 | 责任和关键字段 | 是否可变 |
|---|---|---|
| `PreparationPlan` | 源/用户输入副本、document 哈希、读取关系、提取配置；format=epubox-preparation-1 | parsed_ready 后不可变 |
| `TermPreparation` | 提取计划、各窗口记录、候选池、冻结意图；复用单写入器 | 记录按版本更新；freeze 后封存 |
| `BookPlan` | preparation 哈希、冻结 glossary 哈希、源任务清单、翻译配置 | translation ready 后不可变 |
| `DocumentPlan` | 一份 XHTML/NCX/OPF 资源的源结构、源槽位、Unit、引用表、边界关系 | 提取完成后不可变 |
| `Unit` | 稳定 unit_id、类型、源槽位、投影、源视图/语境引用、注册表；不含最终词条 | 源表示不可变 |
| `CutPlan` | 属于一个 Unit 的 `plan_epoch`、连续源区间、Segment、虚拟边界与哈希 | 新版本替换，不原地编辑旧版本 |
| `RequestManifest` | stage/owner、request_id、输入/wire 哈希和 attempts；正文另有 Unit/plan/revision | 请求身份派发后不可变；attempt 状态原子追加 |
| `UnitRecord` | 当前 CutPlan、候选、已接受译文、revision、校对、问题、尝试计数 | 单写入器原子提交 |
| `DocumentStatus` | 本章候选版本向量、衔接检查记录、局部未决问题 | 可派生/可重算，不替代 UnitRecord |

这些都是本地文件和值对象，不按对象数量建设独立服务。属性、导航、元数据用相同 Unit/Result 契约，只有提取与装配适配器不同。`ResumeDecision` 只是本地纯规划函数的输出值，不新增数据库表或服务；实际状态仍以原有 JSON 为准。

**持久化是契约的一部分：** PreparationPlan 对应 `preparation.json`；术语文件见 §7/§10；BookPlan 对应 `bookplan.json`；DocumentPlan 对应 `documents/<document_id>.json`；Unit 源定义内嵌于 DocumentPlan；UnitRecord 对应 `units/<unit_id>.json`；DocumentStatus/衔接结果对应 `checks/<document_id>.json`。不得只在内存保存 DOM、Unit 或注册表，到整书完成后才补写 JSON。具体字段和保存时点见 §10。

### 2.2 Unit、Segment、Batch 不是同一概念

Unit 决定语义归属和回填；Segment 只解决一个 Unit 确实过长的问题；Batch 只用于传输组批。更改并发和组批不改变 Unit，也不删除仍有效的译文。切点变化可能影响译文，所以只使**该 Unit 的全部 Segment 和相关校对**失效，不试图自动拼用新旧切片。

批次内容变化可能影响模型实际输出，不承诺两次生成完全相同。缓存接受规则基于固定源文、声明的语境、术语和协议；另外保存实际请求哈希用于复现。模型不得依赖同批其他待译项补充上下文；需要的信息必须放进显式只读语境。

### 2.3 冻结输入与允许的局部变化

同一运行中，源书、目标语言、保护策略、提取/翻译/校对提示与模型配置、用户词表副本固定。自动候选只在准备期收集，freeze 提交后生效词表也固定。更换这些输入或启用新词表须新建运行；普通恢复不重新提取/冻结。预算追加属于显式授权记录，不改变语义配置或清空历史计数。MVP 不实现任意配置变化的精细增量缓存或自动词表依赖传播。

运行内允许：有界重试、单元修订、该 Unit 的 CutPlan 升级、重新执行过期的章节衔接检查。更改 CutPlan 时，**不可变 BookPlan/DocumentPlan 不变**；新切片与状态一起写入 UnitRecord，从而解决“源计划不可变却要原地重规划”的冲突。


### 2.4 哈希与版本的唯一含义

`source_hash` 是源 EPUB 字节哈希；准备期 `extraction_input_hash` 覆盖源视图/上下文哈希、相关用户词条、提取策略/提示/模型配置，不依赖尚不存在的正式 glossary。`logical_hash` 覆盖 Unit 源内容、保护/移动规则、目标语言、固定源语境、适用术语、提取/协议/提示版本和模型生成配置；`plan_hash` 覆盖当前 CutPlan（未切片时也有单片计划）；`input_hash = hash(logical_hash, plan_hash)`。这些正式翻译哈希仅在词表冻结后创建并保存在 UnitRecord/CutPlan，不反向写进 DocumentPlan。

`target_hash` 取当前完整目标事件流/切片集合的确定性序列化；`revision` 是该 Unit 当前目标生成代次的单调版本号，不随重规划归零；该代次可先只有部分 Segment 结果，完整候选要等全部必要片段到齐。校对记录绑定 input_hash、revision、target_hash、校对配置和该次实际语境哈希。实际请求另存 `wire_hash`，包含完整消息而不保存密钥。RequestManifest 同时保存本次实际发送的 `term_ids/terms_hash/context_hash` 与 frozen glossary 身份，不能等响应回来后重新选择词条再猜本次用了什么。

所有哈希输入使用同一版确定性序列化规则，不能直接 hash Python 对象的内存表示。Batch 组成、完成顺序、并发数不参与 Unit 身份；输出排版变更单独保存 output_policy_hash。约束或源义发生变化时不冒充“只改排版”。

**补充 `record_version`，不与 `revision` 混用。** 每次原子保存 UnitRecord（包括错误、用量、某一个 Segment 的进度）增加 record_version；只有主动开始新的目标代次/修订/重规划才推进 revision。相同 plan_epoch/revision 下，互不重叠 Segment 的并发结果可以合并进最新记录，不能因为另一个 Segment 先落盘就被判为整 Unit 过期。协调写入器检查请求身份、对应 item 的输入/目标版本，再以最新 record_version 提交。

初始目标代次在派发前分配并落盘；未形成完整目标时 `target_hash=null`，不能校对或接受完整 Unit。初译重试可填补当前代次尚缺的片段，不另建一个代次而使其他片段作废。修订一个已有目标则创建新代次，未修改的片段只能在本地显式继承后使用。旧代次迟到响应仍拒绝。

---

### 2.5 确定性序列化不是任意字符串拼接

所有摘要输入是具有字段名和类型的 JSON 对象：字段按键排序，编码规则固定，拒绝 NaN/Infinity 和重复键。无语义顺序的 aliases/term ID 集合先去重排序；有含义的源事件、章节顺序、切片顺序和目标字符串绝不排序或统一 strip。相同数据模型得到相同摘要，不承诺任意 JSON 数组换序后哈希不变。

不能用 `source + "→" + target + "|" + category` 一类未转义连接作哈希输入；字段自身含分隔符时不同记录可产生相同连接串。这是编码歧义，不是 SHA-256 被破解。词条摘要包含**实际影响本次提示的** source、target、aliases、scope、mode、match_policy、note 等字段；冻结配置与源语境仍参与 logical_hash。[^U5]

磁盘协议升级为 `epubox-document-3 / epubox-unit-3 / epubox-book-3`，以区分基础源计划与后置术语绑定；新增 preparation/glossary/提取协议各有独立 format。正文模型协议仍为 `epubox-text-1`，校对因可选术语反馈使用 `epubox-review-2`，术语提取为 `epubox-terms-1`。旧磁盘 -1/-2 和旧 review-1 不自动混用；提示版本独立登记。实际仓库已有相容实现可通过显式适配保留，不能凭字段相似直接认领旧结果。

## 3. 提取：语言连续，但源归属可核查

### 3.1 独立源槽位账本

遍历原树的元素 `.text`、子元素 `.tail` 和白名单属性，记录 `node_key + slot_kind + 原字符串 + 处理类别`。一个槽位可以被切成连续源区间，但所有区间必须覆盖原字符串，且没有重复归属。空白不一定入模，却必须有去向。`.tail` 是元素后、父级混合内容中的文字，不能随保护子树无条件复制两次。[^R2]

每个区间只属于：一个应译 Unit、保护内容、结构空白或事先声明的范围外内容。另用独立枚举核对提取覆盖；不能用 chunker 自己输出的数量证明 chunker 没有漏文本。

**结构所有权与属性所有权分开。** 图片子树归保护对象，但其允许翻译的 alt 槽位可归属性 Unit；这不构成重复占有同一正文。代码/公式内部则按 §1 的硬保护范围处理。

### 3.2 语义 Unit 划分

普通段落、标题、引文为完整 Unit；`em/strong/a/span` 不自动切断一句话。多段列表项与嵌套列表递归提取，容器不再次拥有子段文字。`body` 裸文本和相邻内联元素形成虚拟文本区域，遇到块级内容结束；不会为方便回填向原书新增 `<p>`。

表格按单元格或其段落提取，保留 `rowspan/colspan/headers` 等结构。明确的表头关联直接使用；不明确时提供有限相邻行列文字及坐标，不猜测“第一行一定是表头”。图注单独提取，不把整张 figure 的媒体属性送入模型。

对代码空白、`xml:space`、预格式区域不做全局 strip、排版缩进或空白合并。代码中的英文注释不顺带翻译。纯代码/纯结构区域不创建空的模型任务。

### 3.3 保护对象与只读提示

大代码块、图形内部、复杂公式保留在本地。短内联代码也由本地恢复，但可在 `hints` 中提供原始短文字；例如 `finally` 或 `memory_order_relaxed`。这比把所有关键术语隐藏成无信息编号更利于理解。

有确切依赖的代码解释可携带预算内的源签名或原代码片段，不能自动生成未经核实的代码摘要。初译、修复、校对都使用同一投影和注册表，不能在校对阶段重新塞入全章 HTML。

## 4. 受限格式协议与中文改序

### 4.1 三种本地引用

| 形式 | 含义 | 装配行为 |
|---|---|---|
| `⟦+g1⟧…⟦-g1⟧` | 可译文字的原始内联范围，如强调/链接 | 用本地原标签/属性创建一次范围 |
| `⟦=x1⟧` | 不可改写的原子对象，如代码、公式、图片、脚注引用 | 恢复一次原子对象；根 tail 不随对象复制 |
| `⟦+b1⟧…⟦-b1⟧` | 本地虚拟约束区间，仅在硬边界附近使用 | 验证边界后消去，不生成新 HTML 元素 |

普通无格式段落只传文本，不添加逐词 ID。属性/纯文本元数据 Unit 只返回文字，不接受控制标记；字面定界符仍遵守转义规则。白名单属性只适用于 §1 明确允许的区域，不能借此把硬保护公式内部改写。

`g` 保存原节点身份、原父范围、是否允许同父改序及源覆盖文字；`x` 保存原子子树、原父范围、边界类型和只读提示；`b` 保存原区间、父范围及固定顺序。原始 href、class、style、命名空间和长属性不进入输出协议。

### 4.2 可实际执行的移动规则

普通 g 与非硬边界 x 可以在获得许可的**同一父范围、同一 b 区间**内整体移动；内部父子关系不变。不同 g 不因标签名相同就互换身份。禁止删除、复制、改父节点、跨 Unit、拆成不连续范围或把两个原范围合并。

脚注引用作为 x 保留 href/注号；同一父范围内多个注号的相对顺序默认固定。其周围文字可以自然调整，但**仅保留位置/次数不能证明脚注仍指向同一论断**。源引用附近原文、目标附近译文及必要脚注正文进入绑定审查，不把程序推测宣称成确定语义。

`br`、页码标记或明确的结构空锚点需要硬边界时，在其原父内容流中建立 b 区间，固定 `b1 → x1 → b2`；包含硬边界的祖先范围向 Unit 根逐层锁定相关兄弟顺序。虚拟区间在原树嵌套内生成，不能跨越原 g 造成交叉。仍发送完整 Unit 的投影以便理解，不对每个 `.text/.tail` 单独调用模型。

若某一源布局无法生成合法、无重叠的约束区间，准备阶段报告该 Unit，保留其他 Unit 的可处理状态；不通过静默删除锚点解决。普通 wbr 不等同于页码：保留对象，在原父范围内按中文断行意义审查，不承诺它对应原英文字符偏移。

### 4.3 改序示例：身份跟着含义走

```html
<p>Compared with <a href="#ssd">an SSD</a>, <a href="#hdd">an HDD</a> is slower.</p>
```

本地定义 `g1 → #ssd`、`g2 → #hdd`。一条合法目标投影是：

```text
⟦+g2⟧机械硬盘⟦-g2⟧比⟦+g1⟧固态硬盘⟦-g1⟧慢。
```

由本地生成对应链接，不按“第一个链接”或源字符偏移猜位置。把 g1 包在“机械硬盘”外面仍可能结构合法，因此 §8 必须检查实际源范围—目标范围含义。这里借鉴 XLIFF 的身份和许可分离，不实现整套 XLIFF。[^R6]

### 4.4 转义、解析与请求身份

投影层先转义反斜杠和字面定界符：反斜杠为 `\\`，字面 `⟦/⟧` 为 `\⟦/\⟧`；之后再交给 JSON 序列化。接收端先解 JSON，再按字符扫描投影转义与合法标记。未知控制 ID、未闭合范围、交叉、重复、悬空转义都拒绝。

普通 `<p>` 字样是文字，写回时作为 XML 文本转义，不能被当成模型新建的 HTML。不能对字符串全局 replace 来恢复对象，也不能先“修复成合法 HTML”再通过。

`input_hash` 不要求模型计算或回传。派发时本地记录 `request_id → 待译 item_id、unit_id、plan_epoch、input_hash、base_revision、注册表`。响应的 request_id/item_id 与这一记录严格匹配；模型不能声明其他 Unit 的完成状态。相同局部 g1 名称只在当前 item 注册表有效，不跨单元查找。

### 4.5 JSON 示例：字段就是实现约定

下面是未切片 Unit 的请求数据部分；系统规则和只读上下文可由现有 SDK 分层承载。

```json
{
  "protocol": "epubox-text-1",
  "request_id": "r001",
  "target_language": "zh-Hans",
  "items": [
    {
      "item_id": "u007",
      "source": "Use ⟦=x1⟧ to release the ⟦+g1⟧resource⟦-g1⟧.",
      "context": {"section": "Exception handling", "previous": "", "next": ""},
      "terms": [],
      "hints": {"x1": "inline code: finally; restore once", "g1": "emphasis: resource"},
      "constraints": {"reorder": "same_parent", "fixed_groups": []}
    }
  ]
}
```

```json
{
  "protocol": "epubox-text-1",
  "request_id": "r001",
  "items": [
    {"item_id": "u007", "target": "使用 ⟦=x1⟧ 释放⟦+g1⟧资源⟦-g1⟧。"}
  ]
}
```

切片时 item_id 由本地生成并关联 `unit_id/plan_epoch/segment_id`，不依赖模型拆字符串推断。条件较复杂时 constraints 还包含 b 区间和各引用的父范围；不把原 DOM 传给模型。

响应整体必须完整解析，拒绝重复 JSON 键、非法数值和异常深度/大小；Python 默认解析对重复键较宽松，需要显式收紧。[^R7] 顶层 protocol/request_id/字段结构不合法时整批无效；合法顶层中的单个 item 字段或标记错误只拒绝该项，未知 item_id 不写入任何 Unit。缺项只影响缺失项；同 ID 重复的全部候选无效；其他独立项通过验证后可保存。**JSON 截断或整体无效时，不从半截数组抢救子对象。**

字段类型合法仍不足以写入 XHTML：目标中 XML 不允许的字符、孤立代理字符和无效编码序列必须拒绝，不静默删字修复。对白名单属性使用同一检查，文本经 XML API 正确转义。

## 5. MVP 样式策略：保留保护，但不做 CSS 引擎

### 5.1 纠正原例子的解释

`p > a:first-child` 匹配的是“作为 p 第一个元素子节点的 a”，不是任意情况下的“p 中第一个链接”。若前面已有 em，它可能一个链接也不匹配。位置伪类和兄弟组合器确实会使元素改序改变匹配对象。[^R3]

### 5.2 有限保守扫描

复用可用 CSS 解析器读取内联样式、style 元素和本地样式表；本地 import 按有限递归读取。MVP 不计算级联、媒体实际生效条件、布局或所有候选排列。扫描结果只有 `reorder_allowed / locked / unknown`。

允许改序的最低要求：依赖读取完整，选择器只使用已支持且不依赖兄弟顺序的类型/class/id/通配/子代/后代组合；条件规则按所有分支可能生效保守收集。涉及位置/兄弟、伪元素、生成内容、计数器、未知选择器或无法解析规则时，不凭正则推定安全。

已知敏感规则能可靠定位时锁定相关父范围；无法定位时锁定该文档的内联对象顺序，而不是删除样式或拒绝整书。明确方向性、ruby、块级显示等结构不当作普通可移动强调范围。MVP 不承诺这类复杂语义结构自动改写；其中已声明外语保留，其他应译文字无法可靠处理时给出局部待处理项。

锁序只限制元素顺序，仍让模型理解完整段落并调整允许的文字表达。若确实无法兼顾自然中文与约束，进入有限修订，然后明确留下最小待处理 Unit；不得把“安全锁死后翻不出来”当作成功。

### 5.3 不夸大样式保证

这项扫描只用于**改序许可**，不能证明所有 CSS 渲染含义不变。目标语言、文字长度、字体回退本来会改变显示。原 CSS 原样保留；不把位置选择器展开成新内联样式，也不新增自动字体优化。

若目标语言或可译属性变化影响 `:lang` 或属性选择器，作为显式目标变化和样本阅读检查处理，不能声称锁住元素顺序就解决了所有样式问题。

测试中的“增加无关长属性不影响翻译”必须真正无关：例如没有样式或规则引用的 `data-trace`。不能任意改变 class/style/translate/href 后仍要求投影和移动策略完全相同。

## 6. 预算、长单元与切片恢复

### 6.1 预算以真实请求为准

`最终输入 I + 输出预留 O + 安全余量 M ≤ 上下文容量 C`，并满足服务商单独输入/输出约束。输入包括系统规则、schema、上下文、术语、投影和 hints；校对输入还包括目标译文。先确保**翻译和校对两个阶段都能装下**，再派发。

有实际 tokenizer 就使用；没有则保守估算并记录误差，不伪造精确 token。输出按中文及 JSON/标记开销预留，不只按英文字符数估算。代码块已经本地保护，不因长属性导致拆分自然语言。

### 6.2 拆分顺序

先缩小 Batch，单个 Unit 仍超限才按源句界/从句边界切分。所有源区间连续覆盖，保护原子和 Unicode 字符簇不能从中截断；缩写、版本号、小数使用项目反例校验，句号不是唯一断句依据。[^R8]

短段、列表短项和短脚注不为了均匀长度拆分。只读邻接源文明确不属于待译内容，不能重复写入目标。所有切片最终仍回到原 Unit，不新增段落或表格格子。

### 6.3 虚拟边界：源范围只恢复一次

CutPlan 在事件流上切分，记录每个边界的原 g/b 范围栈；不截断投影字符串。跨切片的同一 g 使用本地登记的虚拟起止边界，让各切片可独立验证。

```text
源：       g1 开始 —— 内容 A —— 内容 B —— g1 结束
切片 A：  原始 g1 开始 —— A —— 虚拟 g1 结束
切片 B：  虚拟 g1 开始 —— B —— 原始 g1 结束
最终：    原始 g1 开始 —— 译 A + 译 B —— 原始 g1 结束
```

虚拟边界的位置、顺序和层级由 CutPlan 固定，不能被模型挪到切片中间。合并前核对相邻虚拟栈，移除且只移除登记为虚拟的事件；所有实际源事件和原子对象最终恰好使用一次。**“每个引用一次”针对完整 Unit；切片中的虚拟重复按 CutPlan 核对，不能被普通重复检查误拒绝。**

切片不能改变跨边界范围的外侧父关系或跨 b 硬边界搬运内容。拼接不自动加空格、删重复句或移动标点；接缝是否自然由 §8 审查。

### 6.4 重规划：MVP 只支持整 Unit 升级

预算不足、校对装不下或接缝语义冲突时，允许在额度内生成该 Unit 的新 CutPlan：可把需要联合翻译的相邻源区间重新规划，使用更合理的切点。`plan_epoch` 增加，并原子替换 UnitRecord 中的计划和待处理状态。

**该 Unit 旧切片全部不再作为有效结果使用；其他 Unit 保留。** 旧候选可留作诊断；不实现部分新旧切片嫁接。默认最多一次自动重规划，预算不足或仍冲突则待处理，不靠无限拆小保证完成。重规划不清空尝试次数。

不根据英文源偏移切中文。已切片目标按原 segment 身份保存。未切片目标若校对时超限，优先减少批次和非必要响应说明；不悄悄改变已冻结的源语境/词条。仍不够则按上述流程从源重新规划，不能截取中文字符硬凑校对请求。

## 7. 自动术语提取、候选保存、词表冻结与按需注入

**MVP 必须实现翻译前自动术语提取，默认开启。自动提取是词表来源，冻结是本轮翻译期间的一致性规则，两者不冲突。** 用户词表可与自动提取同时使用；不把“用户已有词表”解释为无需补充发现。仅用户在准备配置中显式设置 `auto_extract=false` 时跳过自动调用，这不改变后续翻译与校对标准，也不增加快速翻译模式。

### 7.1 源语境的唯一来源

从已保存的 DocumentPlan.boundaries 和阅读关系选择书名、小节路径及相邻叙述原文，借鉴上游前文尾部/后文开头的短语境机制，不按文件编号 ±1 猜邻居。表格使用明确表头/坐标语境，脚注使用确定的原引用关系；跨文档只有源清单确认的连续阅读边才可提供邻接语境。[^U4]

源结构与源文字视图在准备阶段确定；后续 Unit 不依赖上一 Unit 的译文是否成功。短代码/签名可作只读提示，大段代码、长属性和公式内部不进入术语提取或翻译载荷。每次调用是独立的受控模型请求，不继承前一请求的聊天记录或执行工具。

### 7.2 截取、视图与预算

可选邻接摘录长度为 0 时前后都为空；负数预检拒绝，未配置采用有限默认值。不得用 `text[-n:]` 将零长度前文误变成全文。[^U4] 语境截取优先句界和字符簇，不截断 g/x/b 控制标记；必要表头、已确认词义与保护规则不能归入随意删减项。

新增本地 `SourceTextView` 值对象：`view_id、unit_id、document_id、text、view_hash、source_refs、view_kind`。从源槽位及事件流确定性导出自然语言文字，消去控制标记，保持词序；必要时为块间分隔和普通排版空白使用明确、版本化规则。它不是从译文反推的文本。内联格式两侧的词应组成同一个可理解短语；硬保护对象不展开成可译内容，短代码在独立 hints 中可见。

`source_refs` 关联源槽位区间；较长视图可按源句界切成多个带独立 view_id 的片段，保留连续覆盖。**视图可用于术语出处、选词和只读上下文，绝不能用于按源字符偏移回填中文。** 不建立全书逐词源译对齐。

### 7.3 固定的术语准备流程

```text
保存并核验各 document JSON 与用户词表副本
  → 提交 parsed_ready 的 preparation.json
  → 从 JSON 创建提取窗口及 glossary/plan.json
  → 按窗口调用 TermExtractor，逐项保存成功、拒绝候选或局部失败
  → 本地证据检查、候选去重与用户词表优先合并
  → 有限的冲突定向核对；仍不明的候选不启用
  → 封存候选及覆盖报告，提交冻结意图
  → 原子保存 glossary.json
  → 绑定词条并初始化 UnitRecord/CutPlan
  → 最后提交 ready 的 bookplan.json，允许正式翻译
```

前面的基础解析不能依赖尚未生成的词表。**DocumentPlan 只保存源定义，不保存生效词条或依赖词条的 logical_hash；这些值在词表冻结后存于 UnitRecord/CutPlan。** 这样不需要为了加术语而重写不可变 document JSON。

上游通过 Skill 指导宿主模型建立种子词表，再由 Python 处理存储、匹配与反馈；epubox 将“模型识别候选”实现为现有模型适配器上的固定调用，而不是依赖自由行动的宿主 Agent。上游读写、频次和候选合并机制的适配范围见 §17。[^U1][^U5][^U7]

### 7.4 默认逐章覆盖，不以五点抽样代替全书提取

默认按文档和源阅读关系，把所有范围内可译自然语言视图安排到有界提取窗口。标题、表格文字、脚注/尾注和图注均纳入；独立属性/导航/元数据可以组成小窗口。代码、公式内部、图像像素、长属性以及事先声明不译的内容不参与。无法形成可靠视图的局部源范围必须留在覆盖报告，不能通过删分母隐藏。

提取窗口与翻译 Unit/CutPlan 不同：窗口只是术语准备的一次逻辑工作项，不能改变翻译单元或源结构。长章节按输入/输出预算分窗；不会把整章 HTML 发给模型。每个主视图区间恰好由一个窗口负责；为避免切点遗漏，可附邻接只读视图，但它不重复计入覆盖率和频次。只出现在只读上下文中的候选不能假装是当前窗口发现的主内容，需回到真正负责的源视图取得证据。

`glossary/plan.json` 保存全部窗口的稳定 `extraction_item_id、view_ids、primary_ranges、context_refs、extraction_input_hash` 和初始额度。一个 HTTP Batch 可携带数个窗口，但稳定窗口身份、已成功结果与费用计数不随组批改变。规划时预留候选输出空间；不为凑齐固定词数让模型编造词条，也不在本地用固定 50 条切掉已返回的有效候选。

“全书提取”表示规划覆盖了应扫描的源输入，不表示模型找出了所有术语。报告分别列输入覆盖、有效响应覆盖、候选数、采用数、冲突与缺口，不提供未经验证的术语召回率。

### 7.5 提取协议：模型只提建议，源身份由本地确认

提取请求协议为 `epubox-terms-1`，独立于正文翻译协议。示例文字均为合成数据，实际哈希由本地生成。

```json
{
  "protocol": "epubox-terms-1",
  "request_id": "tr001",
  "target_language": "zh-Hans",
  "items": [
    {
      "item_id": "te_d001_001",
      "document_id": "d001",
      "views": [
        {"view_id": "v_u001", "unit_id": "u001", "text": "The process allocates memory."}
      ],
      "context": {"section": "Computer storage"},
      "hints": [],
      "user_terms": []
    }
  ]
}
```

```json
{
  "protocol": "epubox-terms-1",
  "request_id": "tr001",
  "items": [
    {
      "item_id": "te_d001_001",
      "candidates": [
        {
          "source": "memory",
          "target": "内存",
          "category": "term",
          "aliases": [],
          "scope_hint": "document",
          "note": "用于计算机存储语境，不用于人的记忆。",
          "evidence": [
            {"view_id": "v_u001", "source_quote": "The process allocates memory."}
          ]
        }
      ]
    }
  ]
}
```

响应 item 必须包含 `candidates` 数组，明确没有候选时为 `[]`，不等同于请求失败或漏项。`source/target` 为非空字符串；`category` 限 `term/person/organization/product/abbreviation/other`；`scope_hint` 限 `document/book`，只是建议；`aliases` 为字符串数组，`evidence` 必须有至少一个来源。所有字段有合理长度/响应体上限，超过时拒绝或缩批，不静默截目标译法。未知字段、重复 JSON 键、错误请求身份、整体截断按 §4.5 同等严格处理；合法批中错误 item 不影响其他独立项。

每个候选的 `candidate_id`、源资源/Unit、原始响应归属、候选状态和生效 mode 都由本地赋值。模型不得输出 accepted、required、可信哈希、文件路径或任意 scope ID。`user_terms` 仅含窗口实际相关的用户词条，作为不得覆盖的约束，不重复塞入整本词表。

### 7.6 源证据、候选去重与频次

本地逐候选核验：view_id 属于本次窗口的主视图；source_quote 是该视图 text 中确实存在的连续文本；source 按声明匹配规则出现在证据中。证据中的大小写与标点按实际视图核验，不能用模糊相似度修造引文。由本地补齐 unit_id/document_id/source_refs 和证据状态；模型引用了另一个窗口的 ID、只读提示或虚构句子时，该候选记 `rejected_evidence`。其余有效候选仍可保存，错误不会迫使整章丢掉全部发现。

别名每个都要有实际源出现证据；“字符串真的出现”不证明它与主词同义。只有可明确核实的原文定义关系、用户确认或有限语义核对通过才成为生效 alias。无法确认的别名留在候选记录，不带入匹配器；不因为 API 名、缩写看起来相似就合并实体。

去重键采用结构化编码的源写法、目标写法、匹配策略和适用范围；并保留不同 note/义项产生冲突的可能性。完全相同候选仅合并证据；重复 request/item 响应幂等处理，不增加候选数、证据次数或 record_version 之外的业务版本。单写入器按最新候选记录合并，不能覆盖其他窗口的结果。

频次从**源视图主内容**扫描已知词条及其已确认别名，不扫描译文、上下文重复副本或原始 HTML。重叠别名按同一 term 的不重复源区间计数；不同来源的同一证据先去重。频次只用于诊断/展示，不证明译法正确、不将 preferred 升级为 required，也不能替代“发现新术语”的模型步骤。[^U5]

### 7.7 采用、冲突与作用范围：用户优先，自动建议不硬锁

用户词表在任何付费调用前校验、标准化并保存到 `glossary/user.json`；用户指定的坏 JSON/非法结构报错，缺少指定文件不能当空词表。未指定用户文件时保存显式空副本。旧 source/target 格式可由已有导入器适配，默认 `aliases=[]、scope={kind:book}、mode=preferred、match_policy=exact、note=""`；已有明确硬规则必须显式映射，不默默降级。

标准 scope 为三选一：`{"kind":"book"}`、`{"kind":"documents","document_ids":[...]}`、`{"kind":"units","unit_ids":[...]}`；ID 必须来自本次源清单。空 ID 数组不表示全书适用，直接拒绝。其他 schema 形式不能混在同一快照里。

| 候选情况 | 唯一处理规则 |
|---|---|
| 与用户词条在同一匹配写法/别名及适用 Unit 上一致 | 保留用户规则；自动证据可记录，不改 mode、note 或目标 |
| 与用户词条在同一适用范围冲突 | 用户规则优先；自动候选标 `shadowed_by_user`，不自动覆盖或扩大用户词义 |
| 用户规则自身在同一源适用范围互相冲突 | 可定位时该范围局部 needs_attention，其他任务继续；不能可靠定位时预检停止 |
| 自动候选有真实出处、目标合法且无未决冲突 | 可自动采用为 `preferred`，origin 为 `model_extraction`；不要求每条人工点确认 |
| 同词不同译法出现在不同明确源范围 | 分开保存义项说明与 scope，不强制全书 source/alias 唯一 |
| 同一范围出现不同译法或别名/义项不明 | 有限定向核对；仍不明则 `deferred_conflict`，不自动择高频/最高置信度者 |
| 虚构引文、非法目标、指向不存在源身份 | 拒绝该候选，记录原因，其他候选继续 |

自动候选默认 `mode=preferred、match_policy=exact`，先限制到来源文档；同文档内确实存在多义冲突时可缩到已证实的 Unit 集合。相同译法来自多个文档时可合并其 document_ids，不因“暂未发现冲突”自动推广到全书。模型的 scope_hint=book 不构成全书授权。用户可在**新运行的输入词表**中明确提升范围或规则强度。

对用户规则与自动候选仅部分范围重叠的情况，按本次已知 Unit 集合计算有效范围；用户规则优先的范围内不注入竞争自动词条，其余范围可保留为明确 Unit scope。不能修改用户原文件或用“更窄的自动 scope”绕过用户优先级。

定向核对复用现有模型适配器和调度器，每个冲突组最多一次逻辑调用，不做多数投票、性别属性链或全书在线词义平台。请求含候选 IDs、实际引文及局部原文；响应只允许选择已有候选、将范围缩到请求允许的源 IDs，或 `defer`。不得创建新译法、扩大范围、改 user 规则或产生 required。完整源证据仍须本地检查；语义核对通过不等于数学证明。

核对协议使用 `epubox-term-resolution-1`：本地请求绑定 group_id、group_input_hash、candidate_ids、allowed_unit_ids 和引文。响应只回显 protocol/request_id/group_id，并返回 `decision=select/defer`、`selected_candidate_ids`、可选 `restricted_unit_ids`、`reason`；defer 的选择列表必须为空。select 的候选/Unit 必须都属于请求集合，不能造成仍互相冲突的同源规则同时生效；不合法响应按本组失败延期，不触发无界核对。证据、mode 和用户优先级仍由本地执行。

候选池记录 `proposed / adopted_preferred / shadowed_by_user / deferred_conflict / rejected_evidence / rejected_schema`，以及采用/拒绝原因、证据、来源请求、record_version；冲突组保存输入哈希、核对状态和额度。冻结前所有候选都必须有明确最终处置，不能留着 proposed 却声称池已处理完。异步提取结果先各自落盘，候选池由单写入器收集；所有窗口终结后才完成冲突判定与快照，结果返回顺序不改变采用规则。

### 7.8 提取失败仍继续，但不把失败写成空词表成功

窗口状态为 `pending / in_flight / retry_wait / succeeded / succeeded_with_rejections / failed_exhausted / unplannable`。前两种成功状态都表示收到了完整、已校验响应；`candidates=[]` 的合法成功与请求失败必须可区分。局部失败/拒绝候选后，继续其他窗口；坏证据不改写其他合法发现。

所有窗口都已成功或明确终结为局部缺口，冲突处理也已结束，才允许封存。不存在遗留 pending、in_flight 或本轮尚可自动到期的 retry_wait。**账户/预算/用户取消等全局暂停时不得把剩余窗口改成失败并提前冻结。** 恢复继续未完成工作；额度内请求失败可自动补做，失败耗尽不无限回环。

提取是翻译质量增强，不是正文翻译完成的替代门槛。仅自动提取有局部缺口时，默认可用已验证候选和用户词表冻结，并记录 `extraction_status=closed_with_gaps` 后继续正文翻译；即使没有采用任何自动词条，也须分别保留失败覆盖和实际空候选证据。显式关闭时为 `disabled`；没有可提取输入时为 `not_required`；输入覆盖已处理、无失败窗口时为 `closed`。拒绝候选/延期冲突另列计数，不隐藏在 closed 中。

这些警告不自动阻断正式 EPUB，但后续发现的真实错义、强制规则冲突或重大术语不一致仍按 §8 阻断相应 Unit/发布。不得把“提取阶段允许部分覆盖”扩大成“正文漏译也能发布”。

### 7.9 生效快照与版本：只冻结一次

`glossary.json` 为本轮唯一生效词表，格式 `epubox-glossary-1`，含 source_hash、freeze_id、提取配置哈希、用户词表来源、覆盖结论、warnings、terms。每个词条保存 `term_id、source、target、aliases、scope、mode、match_policy、note、origin、candidate_ids、evidence`；可选 frequency 仅用于诊断。无 terms 仍是合法快照，但必须解释为何为空。

术语示例（记录形状示例，不代表真实书证据）：

```json
{
  "term_id": "t_memory_d001",
  "source": "memory",
  "target": "内存",
  "aliases": [],
  "scope": {"kind": "documents", "document_ids": ["d001"]},
  "mode": "preferred",
  "match_policy": "exact",
  "note": "计算机存储语境，不用于人的记忆。",
  "origin": "model_extraction",
  "candidate_ids": ["c_te001_memory"],
  "evidence": [
    {"view_id": "v_u001", "unit_id": "u001", "source_quote": "The process allocates memory.", "evidence_check": "source_matched"}
  ]
}
```

`schema/format` 表示文件结构；freeze_id 表示本轮冻结身份；`glossary_file_sha256` 表示最终文件字节完整性。`rules_hash` 只覆盖按稳定 term_id 排序的生效提示字段，频次、证据数量、提取时间和模型置信度不参与词义规则哈希；字段明确为 term_id/source/target/aliases/scope/mode/match_policy/note。取舍依据是“是否影响实际提示”，不是把 note 任意忽略。term_id 是本地生成的稳定身份，不使用模型给出的编号作为权威。

准备阶段先原子写 `glossary/freeze.json`：其中保存精确 `snapshot_payload`、输入池/用户副本/源计划哈希、规则哈希和覆盖摘要，再从这个载荷生成 glossary.json；最后才创建翻译计划。候选收集和核对已收口、无在途提取后才能冻结。freeze.json 一旦有效，普通续跑只重放完全相同的快照，不继续更新这个候选池；迟到提取结果只作诊断，不并入快照。状态文件/意图损坏时显式修复或新运行，不凭重新调用模型“复原同一本词表”。

一旦 bookplan ready，所有正式翻译、修复、校对都使用该冻结快照。用户原文件或候选建议后来改变，不会影响本轮。需要启用新词表就按 §2.3 新建运行；MVP 不做自动跨运行缓存迁移或精细历史词表失效传播。

### 7.10 按内容注入，不把整本词表塞入每个请求

先根据**词条适用的源 Unit**过滤 scope，再匹配当前 item 的可译源视图与必要 hints。上下文视图中的命中必须使用它自身的源 Unit 解释 scope，标为只读 context 用途；不能让“上一章适用的 memory=内存”变成本章人的记忆的强制规则。scope 比对先按单位身份实施，短 hints 上的代码术语只提供解释，不能被自动改写。当前目标适用项与只读提示项分开记录并标明作用，不以本段必须出现上一段的目标词作为验收条件。

英语边界/别名匹配可适配上游 `_count_in_text`，补 `C++/.NET、cat/category、所有格、大小写、重叠别名` 反例。exact 保留大小写；casefold 仅在用户明确配置时启用。频次不决定强规则是否注入；同 term 的重复别名命中只注入一次；所有发送顺序按稳定身份排序。[^U5]

不无条件补全书 top-20，不用 max_terms=50 静默截掉已匹配规则。先缩 Batch，再按源合理重规划；仍装不下时该 Unit 记 terms_budget_exceeded，其他任务继续。词条/必要语境都是本次输入的一部分，不能为了省 token 暗中改它们；自动候选阶段可以将不可靠建议延期，但**冻结后已选定的本次规则不得静默删除**。

每个初始/重规划 Segment 的 selected_term_ids、term_applicability、terms_hash、context_hash 在 CutPlan 中确定并保存，terms_hash 覆盖真实发送内容及适用角色。RequestManifest 复制已确定子集与 glossary 身份，派发前核对，返回后不重新查“当前词表”猜历史输入。根据范围与实际目标检查强规则；preferred 允许有依据的自然变体，不能强迫普通多义词逐字一致。

### 7.11 翻译中继续保存建议，但不改本轮规则

初译协议 `epubox-text-1` 保持只返回译文，避免为每次输出新增必需的庞大 meta。新词、更好译法或别名线索由既有源译校对的可选 `term_suggestions` 提供；未提供等同没有建议，不增加一次专门的全书发现调用。review 提示明确这一可选能力，协议版本升级为 `epubox-review-2`，详见 §8.3。

协调写入器将有实际源证据的建议保存在 UnitRecord.term_feedback，绑定 request/item/base_revision/view_hash，模型不能指示生效。重复响应幂等合并，不重新增加候选。反馈可被报告集中列出或作为**新运行**用户词表的素材，不写回已冻结的 candidates.json/glossary.json。后续章节继续使用同一快照，避免不同批次规则漂移。

“更偏好另一译法”只是建议；已确认会改变句义、违反用户 required/keep_source 或造成严重不一致时，review 必须另报对应 major/critical issue，不能藏在非阻断 feedback 中。修订正文仍走完整校对；已明确错误的硬词表本身无法在本轮安全修正时，将受影响 Unit 待处理，用户以正确配置开启新运行。不靠偷偷改词表或回滚已知错误来获得 completed。

### 7.12 与上游的迁入边界

迁入价值集中在词表读写/严格校验、边界匹配与别名、源词频、结构化哈希、候选反馈及幂等归并。其输入从 chunk Markdown 改为源 JSON 视图，Skill 的模型提取改为 TermExtractor；保存统一使用现有 store。保留源出处但不把“引用存在”当成译法证明。

不照搬全书 source/alias 唯一、性别等实体属性共识、批后自动更改 canonical glossary、依据支持次数自动升置信度，以及重新登记输出就算通过的路线。**自动提取和保存现在是 MVP 主功能，不再被排除为“自动术语平台”；暂不做的是动态词表平台。**

## 8. 校对与衔接：有限、可恢复、不会误晋级

### 8.1 Unit 状态与接受条件

```text
pending → translating → candidate → local_valid → reviewing
  → no_change 且校对条件满足 → accepted
  → replace → 新候选 → 本地验证 → 一次完整复核 → accepted / needs_attention
  → needs_attention / 校对失败 → 保留有效候选，不晋级
```

`accepted` 只表示**当前 Unit 的指定译文版本满足单元检查**。章节衔接和最终打包仍可能未完成，因此它不等于全书 `completed`。

每个 UnitRecord 分开保存最新候选、上个有效候选、已接受版本（如有）、本地检查、校对和未解决项。源提取覆盖为 100% 不能证明模型语义无遗漏。

接受条件明确为 `accepted_revision == active_revision`，且输入/目标哈希与本地检查、校对记录一致。新候选选为活跃版本后，旧 accepted 仅作历史保留。若旧译文已有必须修复的问题，修订失败不能通过回滚旧译文来恢复“完成”；该问题保留为局部未决，不中断其他独立任务。无效响应本身不覆盖活跃候选，但其未解决的修复要求仍必须保留。

### 8.2 一次校对覆盖什么

校对是独立于初译的源译对照调用，可以复用同一个模型，但不是让模型沿着自己的初译聊天记录自我肯定。输入包含源投影、候选目标、固定源语境、相关术语，以及**从实际目标事件流提取**的格式覆盖范围。模型不获得文件、代码执行或外部访问工具。

检查五项：`accuracy`（漏义/增义/否定/条件/数值/比较）、`fluency`（自然中文）、`terminology`（适用词条）、`bindings`（链接/强调/注释的含义归属）、`script`（新生成文字的简体要求）。前两项必须实际审查；terminology/bindings 只有本地计划判定确实不适用时才允许 `not_applicable`。不以模型自报置信度放行。

链接源范围 `an SSD` 却覆盖目标“机械硬盘”，或脚注移动到另一论断后，可以结构合法，却应在这一步被识别为绑定问题。结构检查不能替代语义审查，语义审查也不能替代结构检查。

**源证据字段的边界：**借鉴上游候选反馈而不照搬独立自由写入的 meta/动态实体合并。准备期候选按 §7 保存，校对反馈在 UnitRecord.term_feedback 保存。需要帮助定位的 issue 可附可选 `source_quote`；请求身份、源 Unit 和 ref_id 由本地关联。提供的非空 quote 必须确实出现在本次对应的源文字视图中，否则标记该证据无效、保留问题，不凭无效引文自动改规则。纯粹的遗漏/格式问题可以没有 quote，不能伪造引文才能报错。引用确实存在只证明出处，不证明模型判断必然正确。上游 meta 的字符串类型/长度检查不能替代这一校验。[^U7]

### 8.3 校对响应与修订规则

```json
{
  "protocol": "epubox-review-2",
  "request_id": "r002",
  "items": [
    {
      "item_id": "u007",
      "base_revision": 1,
      "decision": "no_change",
      "checks": {
        "accuracy": "pass",
        "fluency": "pass",
        "terminology": "not_applicable",
        "bindings": "pass",
        "script": "pass"
      },
      "issues": []
    }
  ]
}
```

| decision | target 字段 | 处理规则 |
|---|---|---|
| `no_change` | 禁止 | checks 必须满足本地适用性；不得包含未解决的 major/critical 或 uncertain |
| `replace` | 必须是该 item 完整目标 | checks/issues 描述被审查的旧版本；新 target 先成为候选，不能直接 accepted |
| `needs_attention` | 禁止 | 保存问题；不接受、不隐式恢复原文为完成 |

review item 允许额外的可选 `term_suggestions` 数组，默认 []；单条字段沿用 §7.5 的 source/target/category/aliases/note/evidence，scope_hint 可省略并默认 document。本地绑定被审查 Unit 与 source view，不接受模型指定生效词条身份/mode。建议坏字段只使该建议无效并记诊断，不掩盖或删除原有质量 issue；响应整体协议仍严格校验。no_change 可以附非阻断建议，但必需检查必须通过；重大错义必须另有 issue，不能以建议代替。

checks 值限定为 `pass/fail/uncertain/not_applicable`。issue 至少有 `code、severity、message`；severity 为 `minor/major/critical`。minor 可以带明确警告继续；未解决 major/critical、必需检查 fail/uncertain 均阻断。

本地从 RequestManifest 校验 `base_revision + 目标哈希 + plan_epoch`，不让迟到结果覆盖新版本。修订后重新跑**完整的本地检查与五项校对**，不是仅复核原问题，避免改通顺时引入新的否定/数字错误。复核再要求修改或无法判定时进入待处理，不无限“修改—复核”。

对切片，item 对应 segment；响应字段仍叫 `base_revision`，值统一指所属 Unit 的版本，计划版本由本地 RequestManifest 校验。不要为切片再引入语义不同的 base_unit_revision 字段。完整目标修订在同一 UnitRecord 中一次提交；**此前每个 Segment 的成功或失败都已逐项落盘，不等其他 Segment 到齐才保存**。Segment 级审查通过记录可以复用，但只能用于完全相同的目标片段/计划/语境；改动的切片重新审查，所有接缝重新核对。没有任何切片直接写入章节。

### 8.4 章节衔接的有限快照流程

各 Unit 的翻译/校对独立推进，不设“本章全部成功后才开始下一章”的门槛。只有本章**实际参与衔接的全部 Unit 当前版本已 accepted**，才启动本章衔接检查；缺失依赖时记 `blocked_dependency` 及缺失 IDs，不浪费调用、不记为通过，也不阻塞本章剩余任务和后续章节。独立属性、独立元数据不作为叙述衔接的前置依赖。条件齐备后：

1. 冻结该章节的当前 Unit 版本向量和各长 Unit 的目标切片。
2. 按源阅读流生成有限重叠窗口：覆盖长 Unit 的所有切片接缝、同小节连续叙述的相邻 Unit；表格/注释按自己的关系分组，属性和独立元数据不冒充叙述相邻。
3. 窗口同时提供相邻源文和冻结译文，检查指代、称谓、术语与接缝是否自然。窗口只返回问题和所涉 IDs，不返回自由合并的章节译文。
4. 有问题时，在额度内只修订指定 Unit；按 §8.3 重新接受这些 Unit，再冻结新快照。
5. 最多一次自动衔接修订轮次后复查；仍有重大未决项则待处理，不继续传播修订。

长文本窗口可以只截取接缝附近的只读源/目标文本用于上下文；这些截取偏移**不能用于写回**。真正修改仍使用 item 的完整目标或从源升级 CutPlan。

章节检查记录绑定所有参与衔接的 Unit 版本向量；任一参与者后续修改，该章节检查变为过期，需要重做本章固定窗口扫描；独立属性改动不使叙述检查过期。MVP 采用这个粗粒度但明确的规则，不实现动态邻接译文依赖图。其他章节不因本章修订全部重翻。

### 8.5 最小人工修复入口

MVP 不做人工校对 UI，但提供本地修订文件导入能力，避免 `needs_attention` 没有退出路径。修订文件指定 unit_id、base_revision、plan_epoch、完整 target；切片 Unit 提交其完整切片目标集合，不按英文偏移修改中文。

导入产生新候选，重新走同一结构、校对、衔接流程；不能通过编辑 `accepted=true` 绕过验证。过期修订拒绝并给出当前版本。命令名称沿用实际 CLI，新增参数是否为 `--repair-file` 由实现确定，不将示例参数写成当前已存在命令。

## 9. 并发、预算与错误处理

### 9.1 一个调度入口

术语提取/冲突核对、翻译、校对、修复和衔接检查共用现有调度器；按阶段门槛派发，默认网络并发 2，可按当前服务商额度调整。限制已配置的 RPM/TPM 和在途量，429 后退避；不承诺永不遇到服务商限流。

禁用 SDK 隐式重试或把它纳入同一计数。模型超时可能已在远端执行并收费；没有服务商幂等能力时，不承诺请求严格只执行一次。

### 9.2 重试额度不随版本重置

初始上限是工程默认值，不是性能实测：一个初译处理周期内，每个 item 初译 1 次，协议修复最多 1 次，定向重译最多 1 次；正常校对 1 次，修订后完整复核最多 1 次。唯一一次章节衔接修订可启动一个新的指定 Unit 修订/完整复核周期，但仍受下述累计额度约束；不是每产生一个 revision 都能新开周期。传输重试另设不超过 2 次/逻辑请求，并计入实际 HTTP 请求总数。

同时设置**跨 plan_epoch/revision 的 Unit 累计额度**和运行总额度。重规划、协议错误或衔接修订不能清零这些计数。切片数多的 Unit，额度按初始计划规模分配并写入记录：初始默认 `unit_http_limit = 24 × max(1, 初始 Segment 数)`，一次含该 Unit 的实际 HTTP 请求记一次；同批多个 Unit 的归属计数不用于相加计算全局请求数。新增切片使用剩余额度，**该 Unit 耗尽时只将其待做项挂为 needs_attention，继续其他有额度的 Unit**，不能因细分自动无限扩容。章节衔接只读调用另有默认 `6 × 初始窗口数` 的总 HTTP 上限（含重试）；生成式修订仍消耗 Unit 额度。翻译阶段 HTTP 计划上限为各 Unit 额度加衔接额度之和；运行总计还必须包含下述术语准备额度。用户可从运行启动时设置更低的硬总限额，不能直到 bookplan ready 才开始计费/计数。这些上限限制浪费，不保证所有错误分支都能在默认额度内完成。

记录实际请求数、已知输入/输出 token、失败/重试/校对开销。无可靠价格配置不输出伪精确费用；只有已知计费数据才显示金额。预算作用域必须区分：Unit 额度触顶只挂起该 Unit；章节衔接额度触顶只挂起该章衔接检查；**运行总额度触顶才停止全局新派发**。已完成结果保存。额度增加必须由用户明确启动续跑参数执行并记录，不自动调整。

#### 9.2.1 术语准备也有额度，不无限提取或核对

初始默认：每个提取窗口最多初始调用 1 次和内容/协议修复 1 次；每个逻辑请求的传输重试仍不超过 2 次，所以该窗口默认 HTTP 上限 6。冲突组最多 1 次逻辑核对（含传输重试最多 3 次 HTTP）；每运行自动处理冲突组默认不超过 20，按稳定组 ID 选择，超出者明确 defer。以上是可配置的保守工程起点，不是上游实测最佳参数。

初始 N 个窗口确定后，术语准备预算上界 `G = 6 × N + 3 × resolution_group_limit` 在提取前写入计划；没有冲突不实际消耗预留额度。缩批不改变窗口身份；预先必须使一个窗口可装下。极端超限/输出持续截断在修复额度内仍不能完成，记局部缺口，不动态制造无限子窗口扩容。正式翻译预算 T 在词表冻结、初始 CutPlan 完成后确定；无用户更低硬限额时总计划上界为 G+T。T 尚未就绪时只能消耗 G，已经消耗的 G 不会重置。

所有真实 HTTP attempt 都进入同一运行台账；一个 Batch 的共享调用在全局只记一次，归属窗口/Unit 可分别占用其额度但不相加冒充全局次数。预算耗尽、余额/鉴权错误或用户取消为全局 paused，不将未做提取项改成空候选继续冻结；普通单窗耗尽仅终结该窗，其他窗口继续。用户显式追加额度需留授权记录，不清空提取历史。

### 9.3 错误作用域：继续执行与停止发布分开

| 错误/限制 | 最小影响范围 | 本轮必须采取的动作 |
|---|---|---|
| 术语单窗失败、非法候选或冲突无法确认 | 该窗口/候选组 | 记录并继续其他术语任务；阶段终结后按 §7.8 带缺口冻结，不提前跳过尚可执行窗口 |
| 单项漏字段、空译、标记错误、退化、模型明确拒绝当前文本 | item；属于其 Unit 的完成状态受影响 | 保存失败，在有限额度内修复；失败项不得阻止后续 item/Unit/章节 |
| 单项源译校对失败、严重错义/绑定问题、修订复核未通过 | 被审查 item/Unit | 保存候选与问题，不 accepted；其他翻译与校对继续 |
| 完整可解析 Batch 中一个 item 失败 | 该 item | 同批其他独立合法结果分别保存；不回滚整批 |
| Batch 的 JSON 整体截断/不可解析 | 本请求涉及的所有 item | 本批不接受子结果，拆成单 item 请求或缩批重试；其他批次继续 |
| 单个请求暂时超时/可重试网络错误 | 本请求 | 退避后有限重试；没有全局故障证据时不终止整书 |
| Unit 自动尝试或累计额度耗尽 | 该 Unit 的剩余工作 | `needs_attention`，继续其他有额度的 Unit；不得清零计数 |
| 单章衔接失败、衔接额度耗尽或等待失败标题派生导航 | 对应检查/派生依赖 | 挂起该步骤，继续独立翻译任务；失败章不会放行正式输出 |
| 可以明确隔离的局部提取/装配不支持 | 已登记源范围或文档 | 保存源位置和阻断问题，其他已验证独立任务继续；归属无法界定时不能伪装可隔离 |
| 429 | 共享服务商调度 | 共享冷却/降速；恢复后继续；超过本轮服务恢复上限则运行 paused，不将大量任务逐项烧完额度 |
| 鉴权/账户余额/共享模型配置错误，或确认持续不可用的公共服务 | 运行 | paused；停止新网络派发，尽力保存已完成结果 |
| 运行总预算耗尽、用户取消 | 运行 | paused；停止新派发，保存进度；不是删除失败项 |
| 源包/规范预检失败、源身份不符、共享源计划损坏、不可隔离程序异常 | 运行 | failed；不继续基于不可信计划翻译 |
| 磁盘满、写锁丢失、持久化失败 | 运行 | failed；停止新派发，不能继续付费生成无法安全保存的结果 |
| 发布校验/提交失败 | 发布步骤 | failed；保存此前有效译文，修复后重做装配/发布，不自动整书重翻 |
| 迟到响应、人工修订版本过期 | 该响应/修订 | 拒绝覆盖；当前有效工作照常继续 |

§1 的全局输入预检仍先于付费调用；“局部失败继续”不表示读取错误、源书无效或共享存储损坏也强行执行。能隔离的错误必须带确定的 source/document/unit/item ID；无法定位其影响的内部异常不得被 `except Exception: continue` 隐藏。

### 9.4 非 fail-fast 调度：后面的内容必须自动继续

**调度单位是当前阶段可执行 item/步骤，不是“必须全部成功的一章”。** 术语准备使用 parsed_ready 门槛，正式翻译使用 bookplan ready 门槛；不在冻结前提前翻译正文。 稳定源 ID 决定归属；网络完成顺序不决定输出顺序。所有准备完成的文档加入同一个有界就绪队列；不必一次把整书 DOM 载入内存。

执行规则如下：

1. 派发前保存 RequestManifest、额度预留及目标 item 的 in-flight 身份；成功落盘后才发送。每次真实 HTTP 调用分配独立 attempt_id，并在运行总数中记一次；同一逻辑请求的传输重试仍分别计数，不按 Batch 中 Unit 数重复累计运行总数。
2. worker 把**已识别的单项内容/协议/请求错误**转换为带 scope 的结果交给协调写入器，而不是向整书调度层抛出普通未分类异常。
3. 每个成功结果或失败记录立即合并进该阶段的持久记录（提取窗口记录/候选组或 UnitRecord）并原子写入。失败持久化后释放该任务位置，让后续独立任务得到执行机会。不能等整章/整书完成才保存。
4. 常规未尝试任务与已到期重试公平调度。有限的传输重试可在当前 worker 内进行；内容反复失败必须隔离为单项并让出队列，不能靠无限重试卡住下一段。并发设为 1 时也必须继续后续内容。
5. 一条坏结果不能取消其他正常在途任务；全局停止、用户取消与不可隔离故障除外。显式取消应清理后传播，不能被当成普通翻译失败吞掉。
6. 无可执行任务且无在途/本轮可自动到期重试后，先按阶段收口：仅自动提取局部缺口可依 §7.8 继续冻结和正文阶段；正文/校对有未决局部问题则 needs_attention；满足全部发布条件才装配发布。不能在发现首个失败时提前 return，也不能永久等待需要人工解除的 blocked_dependency。

如果项目使用 asyncio TaskGroup，要特别处理其“子任务未处理异常会取消同组其他任务”的行为；应在 worker 边界把已知局部失败转成数据，同时保留全局故障/取消的传播。不能仅替换一个并发 API 就声称失败隔离已经实现。[^R10]

**示例（不表示实测）：** 同章 `u001` 成功、`u002` 翻译失败、`u003` 校对失败、`u004` 成功；下一章 `u005` 也应继续并保存成功结果。本轮结束可以是 needs_attention，但 u004/u005 不能停在未尝试。最终发布仍等待 u002/u003 补齐。

### 9.5 长 Unit、依赖与失败恢复

长 Unit 的 `s1/s2/s3` 共用 CutPlan。s2 失败，s1 的合法目标照常保存，s3 必须继续翻译；不因 Unit 尚未 accepted 就不派发其余 Segment。**同一 plan_epoch 不变时，续跑复用 s1/s3，只补 s2**。仍未齐备时不合并完整目标、不接受 Unit、不写入正式 EPUB。

MVP 可以等长 Unit 的全部翻译片段齐备后再进行完整的片段校对与接缝检查，不必新增逐片依赖传播器；但保存已完成片段是强制要求。只有 §6.4 的**主动 CutPlan 升级**才使该 Unit 全部旧片段过期，不能把普通失败续跑误做整 Unit 重规划。

后续正文使用已保存的源语境和冻结词表，不依赖失败段落的中文译文。衔接检查、标题派生导航等确有依赖的步骤写 `blocked_dependency`，保存所需 IDs/版本；依赖补齐后重新入队。等待依赖不消耗模型请求和重试额度，也不减少必需内容数量。

第一次取消停止派发并尽力保存已返回结果；强制取消可立即终止。恢复从持久 JSON 记录重建状态，不把曾经 in-flight 的请求当成完成。

### 9.6 可解释的只读恢复计划：借鉴 run_state.plan，不复制 record_only

将 §10.5 的恢复表实现为纯函数 `plan_resume(verified_plan, records, checks, now)`，其中 verified_plan 可以是已校验的 preparation 或 ready bookplan，必须先辨明阶段：只读取已经校验的 JSON 快照，为每个 item 或依赖步骤给出 action 和 reasons。不调用模型、不写 accepted、不更新词表、不重置计数、不修文件。CLI 可以输出该规划供检查；它只是派生预览，不成为另一个状态权威。[^U3]

| action | 典型 reason | 实际含义 |
|---|---|---|
| `extract_terms` | `extraction_missing`、`extraction_retry_due` | parsed_ready 后补提取窗口，无正文翻译 |
| `resolve_terms` | `candidate_conflict_ready` | 冻结前的有界候选核对 |
| `freeze_glossary` | `extraction_closed` | 本地构建/重放冻结意图，不调用模型 |
| `prepare_translation` | `glossary_frozen` | 本地绑定词条并完成 ready bookplan |
| `translate` | `missing_target`、`retry_due` | 当前计划中目标确实缺失，且本轮有权限和额度 |
| `validate_local` | `candidate_not_validated` | 目标已保存，仅做本地核验 |
| `review` | `review_missing`、`review_retry_due` | 复用合法译文，只续校对 |
| `check_coherence` | `snapshot_missing_or_stale` | 参与者齐备，仅续本章检查 |
| `derive` | `title_revision_ready` | 可从当前已接受标题生成导航文字 |
| `reuse` | `accepted_current`、`segment_valid_current`、`extraction_current`、`decision_current` | 无模型调用；提取复用不代表正文成功，部分片段复用不等于 Unit accepted |
| `wait_retry` | `retry_not_due` | 到期前不占 worker |
| `wait_dependency` | `missing_source_unit_result` | 不调用模型、不占 worker；依赖补齐再规划 |
| `needs_attention` | `attempts_exhausted`、`untrusted_record`、`repair_required` | 仅局部停留，其他合法任务照常 |
| `stop_run` | `source_identity_mismatch`、`shared_plan_invalid` | 不可隔离的运行级问题 |

调度器执行计划前持有运行写锁，再按 owner_kind 检查对应输入哈希和 record_version；正文另核对 plan_epoch/revision，提取核对 extraction_input_hash，冻结核对池哈希，均须与预览快照一致；不一致就重新规划，不执行陈旧 action。纯预览遇到损坏文件只输出诊断；真正隔离文件/登记失败是协调器显式写动作。缺计划不回退 glob，加载失败不当作初始空状态。

**没有 `record_only` 自动认领分支。** 一个外部目标文件未登记，或已登记 target 的内容与哈希不符，都不是完成证据。只能按 §8.5 显式导入成为新候选并重跑校验；来源/版本/额度不可信时隔离。上游将某些未登记/手改输出转成 record 是其产品选择，本项目不采用。[^U3]

新增入口能力限定为：只读状态/计划预览、执行/续跑、显式重试选定失败项、导入修订；命令名适配当前 CLI，不引入 Agent 编排平台。只读预览可显示 `would_translate / would_review / would_reuse / blocked` 汇总，但必须同时列各项原因。

### 9.7 worker 与请求身份

借鉴每块全新模型上下文，而不是照搬宿主 sub-agent 写文件。worker 只接收一个可信 RequestManifest 的可发送投影并返回 TaskOutcome；RequestManifest 显式含 stage 与 owner_kind/owner_id（extraction_item、resolution_group 或 translation_item），提取期不伪造 Unit revision；文件写入和接受权仍属于协调器。默认沿用并发 2 的工作队列，不改成固定 8 个且必须等整波结束的屏障。普通未做任务、复核与重试公平使用槽位；某项慢或失败不冻结其他独立项。[^U1]

保存源/目标/依赖摘要在派发前绑定，请求完成后不由模型自报“使用了哪些规则”。一个被验证为无改动的 review 也要记录已审查的目标哈希和版本；重复返回按已登记 request/attempt/item 幂等处理，不能反复收费式重新执行，也不能重复推进 revision。实际 HTTP 已发送多次则计数仍分别保留。
