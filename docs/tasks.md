### 1.1 文件命名与长度：全部任务的硬性约束

1. **单词命名**：项目维护的文件统一以一个单词作为文件名主体，扩展名不计入。禁止复合词、多词拼接、连接词拼接，以及用下划线、连字符、空格、驼峰或数字后缀绕过规则。例如 planner.py、terms.py、tasks.md 合规；unit_planner.py、source-map.py、sourceMap.py、sourcemap.py、termsandcontext.py、planner2.py 不合规。不同职责优先通过目录区分，不把目录语义重复拼入文件名。
2. **最多 1000 行**：项目维护的每个文本文件最多 1000 个物理行，代码、注释、空行、文档和测试数据均计入；最后一行即使没有换行符也计一行。1000 行允许，1001 行不允许。禁止通过压缩多条语句、删除必要注释或将内容塞入超长单行规避限制。
3. **适用范围**：覆盖项目维护的源码、测试、脚本、配置、文档和测试夹具；从 M/D/H 复用的文件同样受约束，不能因“原来就这样”而豁免。用户输入、原 EPUB 及其中资源、第三方依赖、历史断点和运行产物仍遵守既有原样保护、命名及恢复合同，不把本条当作改写这些数据的授权。
4. **现有不合规文件**：T00 清点并将改名/拆分责任分配给对应任务，记录旧路径→新路径及引用更新范围。本文与两份源文档已改为 tasks.md/chunking.md/migration.md；下文基线代码路径是定位依据，最终路径及拆分归属以 [文件清单](files.md) 为准。
5. **按职责拆分**：超长文件必须沿现有职责边界拆分，保持行为、导入、CLI、保存格式及恢复兼容性。不得机械按行截断、产生循环依赖，或为了凑行数增加无用抽象。必须由工具约定的固定文件名在 T00 明确列出冲突，不能自行增加豁免或声称已合规。
6. **验收方式**：每个任务检查自己的交付文件；T20 检查全部项目维护文件，不能只检查本次 diff。行数可机械检查；名称除形式检查外还必须人工确认是单个单词，不能把“没有分隔符”误判成合规。任何未解决的命名或行数违规都阻止该任务及整体验收通过。
7. **已授权固定名称例外**：仅保留明确登记的工具约定名称：__init__.py、pyproject.toml、.gitignore、.env.example。uv.lock 为既有依赖工具锁文件。pytest 的 test_ 文件名前缀不作例外，测试发现配置已支持单词文件名；不得借工具例外豁免普通业务文件或 1000 行上限。

### 3.2 不得留给各任务自行发挥的规则

1. **原子归属**：最外层 p/table/em/i/ul/ol 拥有完整范围，后代不重复建任务；一个原子项只由一次完整翻译结果表达。
2. **虚拟文本块**：普通容器的直接 text/tail 可在段落空白或完整句末处分组；不能穿过原子子树、控制标记或字符簇。没有安全边界则报告超限，不新增强制切词策略。
3. **上下文**：同一文档、同一内容通道中，当前 chunk 之前最近最多两个源原子/虚拟文本块，按阅读顺序发送；排除当前成员，各取最近末尾最多 400 字符。零/一个前文也合法。超预算先去掉更早的参考片段，不增加远处背景。
4. **HTML**：必须识别与诊断真正 HTML。能否进入翻译取决于唯一源映射及原子/保护边界验证；不能证明时在模型调用前明确拒绝。本文不增加自动修复或任意 HTML→XHTML 转换功能。
5. **编码**：必须验证 UTF-8、UTF-16、BOM/声明及 CRLF。原编码不能可靠回写目标文字或不能保持保护区间时明确报告，不默默改声明或重编码整份文件。
6. **白名单**：正文外仅处理 C/P 已指定的 head title/描述、NCX 可读导航标签、OPF 书名/简介及 alt/title/aria-label/aria-description 等明确可译属性。资源路径、ID、manifest、spine 和完全保护区域不修改；精确 QName/属性表在 T00 固定，不由调用方临时扩展。
7. **术语终态**：closed、closed_with_gaps、disabled、not_required 可冻结/继续；closed_with_gaps 必须显示警告；paused/open 不得提前进入正文。
8. **正文校对**：顺序固定为初译→校对→应用有效修订→保存。无修订保留候选；有效修订校验后立即存入当前版本；无效/无法修订明确失败，不回退原文冒充成功。不得追加新的多轮 review 策略。
9. **模型输出**：初译只返回 ID 与完整译文；校对只返回所需结论/修订，不重复源文、背景或分析。标记损坏、缺项、截断的结果不能当作该项成功。
10. **恢复边界**：同一冻结任务可复用成功项；身份变化不能静默复用。已完成记录不因重新合批失效，不清空累计用量。

PreparedInput 是对现有 PreparationPipelineResult/最终 ready 索引的最小适配，不是新增执行器。只有同身份的原子预检通过、术语进入允许终态且冻结、所有必需映射与计划已落盘并回读后，才允许交付 ready。词表 closed_with_gaps 可以带明确警告；原子超限或无法可靠回写不能被伪装为准备成功。

请求构造接口固定为“阶段＋有序候选成员＋当前保存目标（review 必需）＋冻结词表＋源索引 → 完整候选载荷”。它接受尚未定稿的成员集合，不依赖已提交的 batch ID。T14 每尝试加入一个完整原子项，就调用 T13 重建这份载荷、排除全部当前成员的重复上下文，再调用 T01 计量，因此不存在“必须先有最终批次才能计算最终批次”的循环。

初译前可以对 review 做保守预算预估；初译保存后，必须用真实目标再次构造并计量 review。若合并批次放不下，只能在完整原子项之间重新分组；一个原子自身仍放不下，则保留其已付费初译并明确阻断 review，不能拆原子或重译来掩盖问题。

预算算法在 T01 固定后供所有阶段共同调用。可复用 D 的 tokenizer 估算、版本和安全余量，以及 M 的完整输出估算，不另造字符/字节冒充 token 的口径。实际供应商分词差异必须标为估算，所有参数/版本写入任务身份。

## 7. 配置/身份变化与恢复判定

| 变化 | 允许复用 | 必须停止静默复用的部分 |
|---|---|---|
| 仅重启、进度报告损坏 | 固定源、计划、词表、成功响应/结果 | 报告可重建，但不能重置实际调用 |
| .env chunk 上限变化 | 已存在任务仍用其保存上限与分组 | 不能自动重切完成块；新配置仅用于明确的新计划 |
| 源文件内容变化 | 旧资料保留 | 原提取、词表证据、译文不能被当作新源结果 |
| 用户词表/作用域变化 | 相同源快照及可证明未变的源索引 | 冻结词表和受影响正文计划/结果不能静默沿用 |
| tokenizer/预算策略变化 | 旧日志按旧版本验证 | 已发送请求身份不改；新预算不能反向篡改旧记录 |
| 模型/提示词/输出协议变化 | 原始资料和历史记录 | 不把旧成功记录当作新配置下未经检查的结果 |
| 解析/原子归属/回填映射变化 | 原始字节快照 | 旧 Unit ID/目标不能直接挂到新原子上；先检查兼容性 |

这张表是“不自动误复用”的边界，不额外要求开发自动跨版本迁移器。明确不兼容的资料必须完整保留，并说明未继续的原因。

## 9. 总体验收与停止条件

全部任务完成的含义是：覆盖矩阵每一行都有对应实现和验收证据，CLI 能按两份需求文档完成准备、翻译、校对修订、保存、恢复及安全出版，且所有项目维护文件满足单词命名和单文件最多 1000 行的约束。

以下情况不能标记全功能完成：原子大于预算却偷偷拆开；术语尚未冻结便开始正文；修订只记录建议未应用；靠整文档重写掩盖 head 变化；旧 JSON 未校验就复用；仍需依靠文档外的新执行器才能运行；只有模拟测试而没有要求的真实小书闭环。

对于文档明确不允许自动处理的输入，正确结果是早期、可定位、零越界派发的错误，保留原始资料。不能为覆盖所有输入而擅自放宽标签、预算、上下文或回写规则。
